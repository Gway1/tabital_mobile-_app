# Screens and the API they use

The mobile app uses the same Flask API as the web app (`Kobydon/tabital`, branch `remediation`). Release builds call the live API, `https://tabital-backend.onrender.com` (`lib/core/config.dart`); `--dart-define=API_BASE_URL=...` points a build elsewhere. The table below lists what each screen calls. Every money amount comes from these responses.

| Screen | Endpoints |
|---|---|
| Sign up | `POST /register` with only `{full_name, business_email, phone, dob, agree, marketing_consent, password, role}` (short form, 2026-10-25). Everything else is added in Verify identity |
| Sign in | `POST /login`, `POST /login/2fa`; forgot password: `POST /forgot-password`, `POST /api/verify-otp`, `POST /reset-password` |
| Home | `GET /customer/upcoming-payments`, `GET /customer/credit`, `GET /customer/instalments`, `GET /customer/notifications/unread-count` |
| Shop list | `GET /customer/products`, `GET /customer/products/categories` |
| Product and plan picker | `GET /customer/products/<id>`, `POST /customer/plan-options` with `{product_id, quantity}` (every plan priced by the server, its schedule, `total_payable`, the credit check and `key_facts`). The app doesn't call `/installment/calculate`, which takes a price from the client |
| Checkout | `POST /customer/purchase` (returns the Paystack `authorization_url` for Payment 1), `GET /customer/payments/config` |
| Payment result | `GET /customer/payments/paystack/verify/<reference>` |
| Plans / plan detail | `GET /customer/instalments`, `GET /customer/instalments/<plan_id>`, `GET /customer/payments/<id>/receipt` |
| Pay | `POST /customer/payments/paystack/initialize` with `{plan_id}`, `{plan_id, amount}` (part) or `{plan_id, settle: true}`; `GET /customer/plans/<id>/settlement-quote` |
| Defer | `GET/POST /customer/plans/<id>/deferment` |
| Saved cards and autopay | `GET /customer/payment-methods`, `PUT /customer/payment-methods/<id>` with `{autopay_enabled}` (the API has no PATCH), `DELETE /customer/payment-methods/<id>` |
| Account | `GET /account/consents` (the Terms version the customer accepted), `PUT /account/consents` with `{marketing_consent}` |
| Verify identity | `GET /customer/identity`, `POST /customer/identity/start`, `POST /customer/identity/<check_id>/submitted`. The selfie check stays off until the Ghana Card number is saved (`details_missing`) |
| Verification checklist | `GET /customer/kyc/details` → `checklist` (`details_missing`, `documents`, `documents_to_upload`, `documents_in_review`, `complete`): shown on Verify identity, and as "Still needed" in the Shop banner |
| Your details | `GET /customer/kyc/details`, `PUT /customer/kyc/details` with only the fields filled in (partial saves); `{error, field}` shows on that field |
| Documents | `POST /customer/documents/upload`, multipart, one document per request (`front_image`, `back_image`, `salary_certificate`, `bank_statement`); upload offered only where `can_upload`. JPG, PNG, WEBP or PDF up to 5 MB, checked in the app first |
| Credit limit | `GET /customer/credit`, `GET /customer/underwriting` |
| Orders | `GET /customer/orders`, `POST /customer/orders/<id>/pay` |
| Report a problem (disputes) | `GET /customer/disputes` (also how the app knows a plan is paused), `POST /customer/disputes` with `{plan_id, reason, description}` |
| Notifications and the bell | `GET /notifications?page&limit`, `PUT /notifications/<id>/read`, `POST /notifications/mark-all-read`, `GET /notifications/unread-count`: the real inbox the reminders write to, as the web app uses. Not the `/customer/notifications*` stubs (backend item 14) |
| Support | `/customer/support/ticket(s)` |
| Account | `PUT /customer/password`, `GET /customer/kyc/status`, `GET /customer/profile` → `status` for the account status card (pending, approved, active, restricted) |

## What the backend still needs for the mobile app

These are small backend changes. They'll be done in the main project when the app reaches them, so the app doesn't work around them.

1. **Returning from Paystack.** Today `PAYSTACK_CALLBACK_URL` points at the web app's `/customer/payment-callback`. The app will open Paystack in an in-app browser and watch for that same URL, then call verify. That works without a backend change. A dedicated app link (`https://app.tabitalpay.com/m/payment-callback` with Android App Links) is a later improvement.
2. **Refresh tokens on a phone.** There's **no refresh endpoint** in `routes.py` yet. For now the app keeps the 60-minute access token in Keystore and sends the customer to sign-in on a 401. `JWT_REFRESH_DAYS` is 1 (evaluation R14), so customers would have to sign in again every day. Proposal: keep that, and add biometric unlock in the app, which re-signs in with a refresh token kept in Keystore. A longer mobile-only refresh lifetime needs a decision (security vs. convenience).
3. **Push notifications.** Add a push channel (Firebase Cloud Messaging) to the message outbox, with a `POST /customer/devices` endpoint to register a phone. Until then, reminders come by SMS (mNotify) and in-app.
4. **Smile ID on mobile.** `POST /customer/identity/start` returns what the web widget needs. The Flutter SDK needs the same job details. Check that the response has everything the SDK asks for.
5. **Device signals (§9D, R27).** The app can send a device ID and an emulator check with sign-in and purchase. The backend's fraud checks already flag more than 2 accounts on one device.
6. **CORS** doesn't apply to a native app. The API's rate limits and security headers apply as they are.
7. **`GET /customer/upcoming-payments` leaves out overdue payments** (it filters `due_date >= now`). Like the web Home, the app builds the next-payment card from `GET /customer/instalments` instead. Fix or retire that endpoint in the main project.
8. **Keep the Paystack callback path.** The app closes its Paystack web view when the page reaches any URL whose path ends in `/payment-callback`, then calls verify with the reference from initialize. If `PAYSTACK_CALLBACK_URL` moves to another path, tell the mobile app (`lib/core/paystack_checkout.dart`, `isPaystackCallback`).
9. **Smile ID from the app needs an on-device test against the Smile ID sandbox.** The app runs Smile ID's `smart-camera-web` (the web app's component) in a web view and uploads to `submit_url` itself, with the `smileid-token` header and the exact `fields` from `POST /customer/identity/start`. No backend change, but confirm with Smile ID that the v3 token isn't tied to a browser origin. Closing the camera doesn't use an attempt (only non-`started` checks count).
10. **`GET /customer/orders` returns a bare list**, not `{orders: [...]}`. The app reads both; nothing to change unless the main project wants one shape everywhere.
12. **With debug off, a missing or expired sign-in token gives 500, not 401.** Found 2026-10-05 running the API with `FLASK_DEBUG=0` (`.claude/dev/run_api_lan.cmd`). `GET /customer/payments/config` without a token logged `flask_praetorian.exceptions.MissingToken ... (401)` and returned **500** ("Server error" alert). With debug on it returns 401. Production runs with debug off, so the web app and the mobile app can't tell "signed out" from "server broken": the app shows "Something went wrong on our side" instead of going to sign-in, and every expired session raises a server alert. Fix in the main project: register an error handler for praetorian's errors (`PraetorianError` → its `status_code` and message) that works whatever the debug setting.
13. **Plan responses don't say a plan is paused by a dispute.** `GET /customer/instalments[/<id>]` has no `paused`/`paused_reason`, so the app reads `GET /customer/disputes` to find an open report for the plan (`plan_detail_screen.dart`). Add `paused_at`/`paused_reason` (or `paused: true` and the dispute id) to the plan response.
14. **Done (X5e, 2026-10-17): the `/customer/notifications*` and `/merchant/notifications*` endpoints read the same inbox as `/notifications`** (services/inbox.py). `GET /customer/notifications` now returns the `/notifications` shape (`notifications`, `total`, `page`, `limit`, `total_pages`) instead of a made-up list; mark-as-read (by id or `NOT…` code), mark-all and the unread count are real, so `GET /customer/notifications/unread-count` (Home's dot) matches the bell. No change is needed in the app: it already uses `/notifications`, and the unread-count key is still `unread_count`.
15. **Password reset is email only, and the emails are off-brand.** Customers sign in with a phone number, but the reset code goes only to `business_email` (no SMS through mNotify). The reset and "password changed" emails use a purple gradient, emoji and "OTP" wording, not the Vault style or the support contact. Consider an SMS code and restyled emails.
16. **Small API notes from the app's review:** the minimum part payment (`min_part_payment`) isn't exposed, so the app can only show the server's refusal after the customer taps Pay; the credit response has no "in plans" amount, so the limit screen's bar shows the proportion without a figure; the down-payment verify response has no merchant name or first due date for the result screen's next steps.
17. **The current Terms version is only in a product's key facts.** `TERMS_VERSION` comes back in `key_facts` (plan-options) and is stored on orders, but no plain endpoint returns it. The Account page shows the version the customer *accepted* (`/account/consents`). To tell a customer when newer Terms apply, expose the current `terms_version` (and `privacy_version`), for example in `GET /customer/payments/config` or a small `GET /legal` endpoint.
11. **The `overpaid` and `duplicate_payment` results promise a refund review, but the main project has no review queue yet (R5.c).** Until it's built, those cases rely on staff noticing them.

## Backend changes from the data architecture remediation

The backend branch `data-architecture-remediation` (2026-10-08) changes these responses. The app isn't edited (it's frozen); each line says what the app does today and what it should do when it's next updated. Tracker: `Reviews/data-architecture/remediation_tracker.md`.

| Item | Endpoint / field | Change | Effect on the app today | When the app is next updated |
|---|---|---|---|---|
| DA-01 | `GET /customer/orders` → `refund_status` | New value `refund_pending`: the order was rejected and the Paystack refund call is in flight (normally for a second; it stays only if the refund call never completed). | `Order.refundNote` returns null for it, so no refund note shows. | Show "Your down payment is being refunded" for `refund_pending`, like `refunded`. |
| DA-04 | `GET /customer/credit` and the limit shown on Shop quotes (`available_limit`) | Values change, not keys: the available limit now also subtracts the full price of the customer's **paid credit orders waiting for approval**, and what's still owed on **defaulted** plans.
